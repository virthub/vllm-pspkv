# Qwen2.5-7B：Basic / Enhanced / BTKV 昇腾对照

2026-10-23 在 worker03 的 Ascend 910B3（NPU 4）完成四配置测试。
使用用户选择的 **Qwen2.5-7B 基础版**，不是 Instruct。

主要结论：三个 PSP-KV 格式均能完成推理，且本轮输出彼此完全相同；
固定单位缩放 E4M3 的缓存容量约为原生 BF16 的两倍，但生成出现明显重复退化，
因此这套 7B 配置的质量验证**未通过**。运行成功与格式间一致不足以证明
模型质量合格，也不能把结果表述为迁移已全面完成。

## 配置和方法

- 镜像 `quay.io/ascend/vllm-ascend:v0.20.2rc1`，ID 见
  [image-id.txt](raw/image-id.txt)。模型权重 BF16，加载约 14.2791 GB。
- TP=1、eager、页长 128、最大模型长度 256、最大并发序列 1、
  `gpu_memory_utilization=0.35`，关闭 prefix caching。
- 原生基线使用镜像自带 vLLM/vLLM-Ascend 与默认 BF16 缓存；
  三格式使用隔离适配层分别调用 `psp_attention_basic/enhanced/btkv`，
  全部使用固定 E4M3、单位缩放、相同原生 packed_scatter 写入器。
- 三个格式的 28 层日志均记录了对应实际入口；测试源码只读挂载，未替换
  服务器项目原文件。代码及库哈希见 [source-sha256.txt](raw/source-sha256.txt)。
- 每配置预热 4 次、计时 24 次（3 轮，每轮每种输入 4 次），另有两个简单
  输出探针，共 30 次生成。四配置合计 120 次生成，96 次计时。
- 短输入 3 token，跨页输入 135 token；每次输出 32 token，temperature=0、
  seed=123、ignore_eos=True，通过 completion 接口测量。
- 跨页输入在 128-token 页边界之后继续解码。这里的“跨页”不代表长上下文
  压力测试；本次实际最大输入加输出仅 167 token。
- 下表为每类 12 个计时请求的中位数；P95 是这 12 个样本的插值估计，
  样本规模不足以替代正式吞吐、尾延迟和稳定性基准。

## 实测结果

| 配置 | 分配器 KV token 容量 | 短输入 +32 token P50 | 跨页输入 +32 token P50 | 输出观察 |
| --- | ---: | ---: | ---: | --- |
| 原生 BF16 | 130,688 | 1.536 s | 1.507 s | 短句连贯 |
| Basic，E4M3 | 261,504 | 1.785 s | 3.280 s | 短句明显重复 |
| Enhanced，E4M3 | 261,504 | 1.780 s | 2.657 s | 与 Basic 完全相同的重复 |
| BTKV 参考兼容，E4M3 | 261,504 | 1.803 s | 2.608 s | 与 Basic 完全相同的重复 |

| 配置 | 短输入 P95 | 跨页 P95 | 短输入 TTFT P50 | 跨页 TTFT P50 | 跨页 TPOT P50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原生 BF16 | 1.583 s | 1.593 s | 104.04 ms | 99.89 ms | 45.38 ms |
| Basic | 1.875 s | 3.425 s | 119.26 ms | 278.57 ms | 96.82 ms |
| Enhanced | 1.928 s | 2.771 s | 118.99 ms | 275.72 ms | 76.67 ms |
| BTKV 参考兼容 | 1.990 s | 2.717 s | 118.38 ms | 273.20 ms | 75.08 ms |

Enhanced、BTKV 的跨页 P50 相比 Basic 分别下降约 19.0%、20.5%。
两者都没有超过原生 BF16。BTKV 与 Enhanced 使用相同的计算与转置 V 布局；
约 1.8% 的本轮端到端差别不足以证明独立硬件加速收益，尤其不能归功于 TMA。

缓存容量是运行时分配器报告的物理页总容量，不是已验证可服务这么长的上下文。
本次最大模型长度被显式限制为 256。三格式 KV 数据容量相同；布局本身没有
额外压缩。测试适配元数据总量：Basic/Enhanced 各 1,201,284 字节，BTKV
8,523,396 字节，其中额外部分是未被 TMA 使用的描述符。
测量后的 EngineCore HBM 占用分别约为：基线 22,116 MB、Basic 22,067 MB、
Enhanced 22,067 MB、BTKV 22,073 MB。缓存预算相同，因此更高容量并不意味着
整个进程的 HBM 减半。

## 输出检查与质量问题

三个格式的全部重复请求，在相同输入下输出逐字一致；两个额外探针的输出也
三格式一致。它们与 BF16 基线的输出均不完全一致。输出不同本身不证明错误，
但本轮短句中出现的强烈重复是明确的质量退化信号。

输入：`北京是中国的`。

- 原生 BF16 开头：`首都，也是中国最大的城市之一。它拥有悠久的历史和丰富的文化遗产……`
- 三格式 E4M3 开头：`首都，也是中国最大的城市之一。。。。。。。之一。之一之一之一之一……`

跨页问题中，四配置均以“北京”开头，但三个 E4M3 格式出现多余标点和重复词，
如“中国的的首都”。两个简单探针不能构成正式质量评测；基础版模型也会继续
补全后文，不能按 Instruct 的对话格式评判全部续写内容。

## 实现边界与跨平台证据

这是显式开启的测试适配层，不是生产后端增加了三格式自动切换开关。
预填充通过公共 eager FP32 注意力，解码进入对应原始算子入口；它与原生基线
的预填充实现也不同，因此基线延迟差异不能全部归因于 KV 位宽。
模型测试固定 E4M3，没有测试自动混合精度策略或 FP4 模型质量。

本轮另在 RTX 4060 Ti 上以相同打包输入运行迁移前的 CUDA 参考设备函数：
108 项校验通过，CUDA—NPU 最大绝对误差 0.0009765625，含 Qwen2.5 的
28 Q 头/4 KV 头结构。详见
[跨平台报告](../2026-10-23-cross-platform/REPORT.zh-CN.md)。
这验证已覆盖输入的参考注意力算术，未覆盖完整 NVIDIA 模型服务、全部真实
模型分布、在线写入器的端到端质量或硬件 TMA。它不能抵消本轮观察到的质量退化。

## BF16 控制实验与量化诊断

为定位退化，保留同一适配层的预填充和 Basic 原生解码，改用 code=0 的无损
BF16 缓存。因插件只分配 FP8 arena，测试为每层另建两个 BF16 shadow 页，
将单序列的物理页映射到逻辑页 0/1，最多覆盖 256 token。该实验用于数值和
输出控制，容量与延迟不纳入上面的公平性能比较。

在 NPU 4 上，控制实验预热两次、计时生成两次、额外探针两次，均成功。
**短句、跨页、算术探针、法国首都探针的 32-token 输出全部与原生 BF16
基线逐字一致**，短句的“之一”重复消失。原始结果见
[BF16 控制输出](bf16-control/basic-serving.json)，
完整命令和适配代码保存在 `bf16-control/`。这把问题缩小到有损 FP8 缓存路径，
但不是对所有输入的接入正确性证明。

首次短句预填充的 28 层诊断中，K 最大绝对值 **418**、V 最大绝对值 **70.5**，
有 12 个 K 元素绝对值达到或超过 248。原始 CUDA 的 E4M3 编码器对 exponent
达到 15 的值统一写 `0x78`（负数加符号位）；其解码器把 `0x78` 解释为 256。
昇腾 `EncodeE4M3` 保留了相同处理规则。

为核实这一点，在 RTX 4060 Ti 上直接调用原始 CUDA 量化头文件中的函数：

| 输入 | 原 CUDA 编码再解码 | PyTorch E4M3FN 编码再解码 |
| --- | ---: | ---: |
| 320 | 256 | 320 |
| 384 | 256 | 384 |
| 418 | 256 | 416 |
| 448 | 256 | 448 |

原始日志和逐项数据见
[CUDA 量化探针](../2026-10-23-cross-platform/cuda-quantization-probe.json)。
因此，**迁移前 CUDA 编码器本身已存在这段大值范围的饱和问题，昇腾编码代码
沿用了它**。真实 7B K 分布触及该范围；此前小幅随机张量测试未覆盖它。
这与本轮退化有关的证据很强，但尚未通过“修复编码器后质量恢复”的实验，
不能宣称它是所有质量问题的唯一原因。本次未修改或修复生产量化内核。

后续应明确并修复 E4M3 格式边界，检查真实 K/V 的在线量化误差和缩放策略，
再重新做 7B 质量评估。没有找到可核验的历史 NVIDIA 完整模型结果，因此仍
不能声称已有跨平台完整模型质量对齐。

本轮五个模型服务容器（四主测试及一控制）均正常退出，见
[final-containers.txt](raw/final-containers.txt)；NPU 2/4 已无测试进程。
测试前后关键源文件和原生库哈希、原工作树状态相同。新增测试工具和报告
相关 pre-commit 检查通过；未重新解决核心迁移代码的存量 mypy 错误。
