# NVIDIA 策略集合对齐及长上下文对照

本轮已完成 NVIDIA 策略集合对齐、四精度优化接线、长上下文融合检查及整模型对照。
结果是：KV 存储密度提升成立，但当前单请求推理时延仍未稳定优于原生 BF16，FP4 输出质量也未达可用。

## 范围及测试方法

NVIDIA 源码固定到 `develop` 的 `00b78e954225947fbd05281fc19bd9f22164f851`。
保留 Basic / Enhanced / BTKV 与 lossless / E4M3 / E5M2 / FP4 两个维度；
幅值自适应另列。RMSE 选择器、分组校准、K8/V4 等均不进入本次主对照。

Ascend 三个格式入口复用公共软件内核，Enhanced / BTKV 的主对照使用分阶段回退路径，
不能把名称不同说成已实现三套不同的硬件优化。BTKV 不使用 CUDA TMA。
直接读取压缩 tile 的融合路径另有数值与性能测试，其 QK/PV 目前在 Vector 上执行。
具体实现位置与限制见 [改动说明](CHANGES.zh-CN.md)。

- 硬件：华为 Ascend 910B3；主对照 Basic / Enhanced / BTKV 分别使用物理卡 4 / 6 / 7。
- 模型：`Qwen/Qwen2.5-7B` 基础版，权重 BF16，TP=1，单并发、单请求调度。
- 输入：严格 3 / 135 / 8192 token；每次固定生成 32 token，temperature=0、seed=123、忽略 EOS。
- 关闭前缀缓存、chunked prefill；block size=128，max model length=8320，显存预算参数 0.35。
- 每个进程各输入长度预热两次，每种长度计时 12 次；随机交替输入长度以检查图中的动态长度。
- 同一张卡顺序运行 BF16-before、四精度、自适应、BF16-after。基线使用原生
  `mode=3`，最终候选使用 `mode=0` 保留 RoPE 适配器；两者均使用完整 decode 图，
  `FULL_DECODE_ONLY, capture_sizes=[1], pa_shape_list=[1]`。
- 候选均开启跨层元数据复用、设备长度复用、直接 strided K/V 写入、RoPE/写入融合、
  同流跨层工作区复用、活跃页向量解码及图重放。没有用 eager BF16 对比 graph 候选。

最终轮为 `serving-v14`，前置基线直接复用同卡、在本轮候选之前完成的
`serving-v9/bf16-after` 的 12 次采样，后置基线在最终轮重新运行。
复用的是相同镜像与启动参数的原生 BF16 数据，不是将更早候选的结果混入最终候选统计。
原始 JSON 的 case 字段仍保留其来源。旧的 `serving-v9` 是完整的编译路径对照，单独归档。

`mode=3` 的 AOT 路径会固化未进入 decode 适配器的模型分支，不能仅凭环境变量声称
RoPE 融合生效。[调用审计](validation/audit-v13) 验证最终捕获路径实际调用
`strategy_rope_scatter`；最终 45 组“入口×精度×长度”的输出集合均与前一轮对应配置一致。
最终候选只补齐分页注意力图参数初始化，由 vendor runner 在图发射后更新任务，
没有重复提交更新。基线保留其可用的原生编译路径；prefill 编译方式的区别也属于本轮实现成本。

同时进程不能共享同一张 NPU 做这轮服务测试；曾遇到 ACL ResourceBusy，已改成顺序设计。
不同卡之间的绝对耗时不用于推断三种格式的算法差异，每个候选只与同卡 BF16 比较。
统计采用候选 12 次与基线前后共 24 次的中位数，速度比为 BF16 / 候选，
95% 区间是按基线阶段分层、独立重采样的 bootstrap，不是配对区间。

原 NVIDIA `scripts/benchmark_psp_kv.py` 提供了三格式、四精度的测试结构。
本轮复用该矩阵与 develop 的 CPU 注意力 oracle；将随机输入生成、缓存构造及 dtype 转换
移出计时，避免原脚本中基线反复生成输入、候选复用输入的额外差异。
没有可用 NVIDIA 服务器或原始运行日志，因此本报告不包含 CUDA 实测速度对比。

## 算子阶段：8192-token 上下文

Qwen2.5-7B 的 28 个 query heads / 4 个 KV heads / head dim 128，单 token decode。
预先构造随机物理页和共享每页每头缩放，对照 develop CPU 参考的实际压缩字节。
单位为毫秒；设备事件计时，图中每次重放连续执行 16 次以摊薄 Python 提交成本。

| 精度 | 仅向量解码 | 解码＋原生分页注意力 | 直接 Vector 融合，Split-K=4 |
| --- | ---: | ---: | ---: |
| lossless | 0.0342 | 0.0896 | 0.5505 |
| E4M3 | 0.0675 | 0.1277 | 0.8566 |
| E5M2 | 0.0671 | 0.1269 | 0.8560 |
| FP4 | 0.2057 | 0.2660 | 1.8839 |

原生 BF16 分页注意力为 **0.0467 ms**。切回成熟的原生注意力消费者后，
FP8 相对 Vector 融合约快 6.7 倍，FP4 约快 7.1 倍；这不是相对 BF16 的加速。
E4M3 的分阶段路径仍约为 BF16 的 2.73 倍耗时。
原始数据见 [设备检查 JSON](validation/checks-v8/result.json)。

较短上下文同样测量了 135 / 1536 token，全部精度均与压缩字节参考通过误差检查。
例如 E4M3 分阶段路径分别约 0.0294 / 0.0501 ms，而 BF16 分别为 0.0193 / 0.0275 ms。

## 首 token 的另一个瓶颈：prefill 编码

新增分阶段计时见 [含写入测量的检查](validation/checks-v9/result.json)。8192 token 下：

| 精度 | K/V 压缩写入，单层 ms | 缩放估计，单层 ms |
| --- | ---: | ---: |
| lossless | 0.595 | 不需要 |
| E4M3 | 7.001 | 0.034 |
| E5M2 | 6.999 | 0.034 |
| FP4 | 6.924 | 0.033 |

缩放估计不是这个阶段的大头。直接写入虽然已省去 stack 和来源副本，
每个数的浮点位编码仍主要用标量指令；8192 token 时 28 层的 FP8 编码成本粗算约 0.196 秒。
它可以解释整模型首 token 差距的量级，但不是对整模型时间线逐个任务的精确归因。

独立整模型接线初测中，相同 E4M3 配置从 Vector 融合换到共享工作区＋原生注意力：
8192-token 请求约 1.961 → 1.363 秒，流式 TPOT 估计约 37.86 → 18.27 ms；
TTFT 约 787 → 797 ms，没有同步改善。对应 BF16 初测约 1.087 秒、TPOT 14.90 ms。
这些分别为 1 / 2 次计时采样的接线检查，v6 / v4 使用卡 2，v8 使用卡 4，
仅说明观测量级，不作为同卡加速结论，也不与主矩阵混合统计。
原始请求分别保存在本目录 `validation/serving-v6`、`serving-v8`、`serving-v4`。

## 容量为何增加，延迟却仍可能变差

真实 KV 页每元素为 BF16 2 byte、FP8 1 byte、FP4 0.5 byte，因而有实际存储收益。
分配器报告的 KV token 是该缓存预算可容纳的逻辑 token 总量，不能当作当前单请求长度，
也不是已经实测达到的吞吐量。权重、运行时、工作区及缩放表不会一起减半。
实际 token 容量也受各路径 profile 峰值和工作区预算影响，不能把路径间的整个比值都归因于量化。
自适应按最坏 FP8 的 1 byte 预算分配逻辑页；即使部分页选择 FP4，也不自动向调度器增加逻辑页数。

分阶段路径解码一层时，仍要读取压缩页、写出 BF16 临时数据，再由注意力读取临时数据。
忽略元数据和复用效果，仅按完整 K/V 字节估算：FP8 为 1＋2＋2=5 byte／元素，
原生 BF16 注意力读取为 2 byte／元素。压缩的是常驻存储，当前实现没有同步减少这条路径的
全部显存流量。工作区跨层复用减少分配及峰值占用，不能省掉不同层各自的解码。

本模型有 GQA：8192-token 时，全模型 28 层的活跃 BF16 K/V 约 448 MiB，
而 BF16 权重约 14 GiB。即使忽略转换成本、假设单请求 decode 每步权重完整流经显存，
把 KV 减半仅减少约 224 MiB，相对这部分总读取量约 1.5%。这是字节量级估算，
不是实测带宽或利用率；它说明本轮单请求长度下，单靠 KV 减半本来就没有很大的整模型加速空间。

直接融合避免该临时 BF16 写回，但当前按 query head 分工，GQA 的多个 query head
重复处理同组 K/V tile，且 QK/PV 没有使用新的 Cube 融合实现，导致长上下文更慢。
这些数据支持“当前算法和执行路径有额外成本”，不能据此断言硬件本身并行能力不足。

后续若继续追求稳定低于 BF16 的时延，应优先完全向量化批量 prefill 编码，并实现按 KV head
复用 tile 的 Vector/Cube 融合注意力，避免 BF16 临时写回。更换布局名字或继续增加标量任务
不能代替这两项工作。高并发吞吐收益还需要独立的多请求实现与基准，本轮单请求结果不能外推。

## 正确性与质量边界

- [CPU 回归](cpu-tests.txt)：85 passed，包含容量预算、旧编码/arena、元数据、图输入契约和新策略选择。
- [原有 NPU 回归](validation/regression-v8.log)：263 passed，覆盖旧三布局与四精度接口、混合格式和复制。
- 新设备检查：四精度各覆盖全部 65,536 种 BF16 位模式；FP8 NaN 的载荷不作跨实现一致性要求。
  FP8 对照 PyTorch 标准有限饱和转换，FP4 对照 CUDA 位编码规则。
- 32 个 RoPE/写入组合对照已安装的 Triton RoPE＋独立写入，输出及缓存字节一致。
- 135 / 1536 / 8192 token × 四精度 × Split-K 1 / 4 / 8 / 16，另测向量解码＋原生注意力。
  新融合路径与 develop 压缩字节注意力参考的最大绝对误差不超过约 0.001。
- 8192 上下文图另外重放长度 3 / 135 / 1536 / 8192 / 17 / 8191，共 24 次，均对照数值参考。
- 混合页 `[E4M3, FP4, E4M3]` 的设备写入和零值缩放回退通过；自适应选择规则另有 CPU 检查。

数值通过表示正确计算了“量化后的注意力”，不表示量化与 BF16 等价。
随机注意力检查中 E4M3 / E5M2 / FP4 相对未量化输出的 L2 偏差约为 3% / 6% / 33%。
本轮文本是基础模型 completion 的小样本，不能替代 PPL、任务准确率或长文理解评估。
精度对照输出观察见主矩阵表；不把 HTTP 200 当作质量达标。
