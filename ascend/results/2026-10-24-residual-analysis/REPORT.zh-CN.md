# 优化后仍慢于原生 BF16：剩余瓶颈实测

本轮检查的是已经完成第一轮优化的 Basic、Enhanced、BTKV 参考兼容实现。
结论是：跨页路径已经使用原生分页注意力，剩余的主要自定义算子成本在调用它之前的
FP8 解码和 BF16 临时缓存生成；短输入仍走旧标量注意力。此外，每层重复准备元数据、
拼接 K/V 和提交多个小算子也有开销。增加工作核数本身不足以解决这些问题。

本轮只增加诊断脚本和结果，没有继续改动上一轮的生产算子或适配代码。

## 测量对象和证据边界

- 华为 Ascend 910B3，物理 NPU 4；容器内逻辑设备 0。
- 使用上一轮验证的 v2 库，SHA256 为
  `6431a9e4782eb78edf21487d0ff455e04bfab0d68414989fea531b08f5250779`。
- 复用最终对照适配器，`OPTIMIZED=1`、`PAGED_MIN_LENGTH=64`。
  当前对照是固定 E4M3、单位缩放，没有运行自动混合精度决策。
- 算子输入采用 Qwen2.5-7B 的头数：28 个 Q 头、4 个 KV 头、维度 128、
  页长 128、batch 1、BF16 Q/O；长度 32、160、512、2048，三格式共 12 组。
- 数据为有界随机张量。每阶段预热 3 次，再测 5 轮、每轮 20 次，取轮均值的中位数。
  所有组的原生注意力、标量参考和优化路径输出通过 `atol=rtol=0.01` 对照。
- 对 Basic 的长度 32 和 160，额外采集实际适配器回调与原生注意力控制的
  Level1 / PipeUtilization 数据，每类调用 3 次。

整模型对照复用[上一轮同日 Qwen2.5-7B 测试](../2026-10-24-optimization/REPORT.zh-CN.md)。
本轮新增的是算子分段测试和硬件流水线采样，没有重新采集完整 7B 模型的逐层时间线。
独立阶段时间不能直接相加：缓存状态、主机提交、同步和流水线重叠都会改变结果。
NPU Event 时间也可能包含主机尚未提交下一任务造成的等待；纯内核执行时间以 profiler 为准。

## 整模型剩余差距主要在逐 token 解码

跨页输入为 135 token，生成 32 token；以下为上一轮客户端测得的 P50：

| 配置 | 整请求 | 首 token 延迟 TTFT | 后续平均 token 间隔 TPOT |
| --- | ---: | ---: | ---: |
| 原生 BF16 | 1.542 s | 100.71 ms | 46.46 ms |
| Basic 优化后 | 1.754 s | 108.61 ms | 52.83 ms |
| Enhanced 优化后 | 1.771 s | 111.47 ms | 53.47 ms |
| BTKV 参考兼容优化后 | 1.710 s | 108.57 ms | 51.77 ms |

首 token 只相差约 8～11 ms；之后每 token 相差约 5.31～7.01 ms，重复生成会累积差距。
若仅为估计量级而平均分到 28 层，相当于每层多约 0.19～0.25 ms。
这不是从完整模型 trace 得出的精确逐层归因。
客户端 TPOT 按流式片段估算，指标中位数之间也不应强行相加。
精确差值见 [model-gap.json](model-gap.json)。

## 跨页路径：解码阶段比原生注意力更贵

当前计算流程是：

```text
原生 BF16：BF16 KV cache → 原生分页注意力
当前 FP8：FP8 KV cache → 解码全部当前活跃页 → BF16 临时 K/V → 原生分页注意力
```

每个解码步、每层都重新生成当前注意力需要的历史 K/V 临时缓存，不只是处理新增 token。
长度 160 时按两个 128-token 页面物化，共生成 512 KiB 临时 BF16 K/V，包含尾部填零。
这些临时数据随后又被原生注意力读取。

在实际 Basic 回调的长度 160 采样中：

| 内核 | 平均设备执行时间 | AIV 标量流水线比例 | AIV 向量流水线比例 |
| --- | ---: | ---: | ---: |
| 并行压缩写入 | 10.87 μs | 91.13% | 0.10% |
| 解码并生成 BF16 临时页 | 164.66 μs | 94.83% | 0.20% |
| 原生分页注意力 | 16.73 μs | 混合矩阵/向量算子 | 混合矩阵/向量算子 |

解码内核约为后续原生注意力的 9.8 倍，是此路径最贵的自定义设备算子。
它已经启动 40 个 AIV 工作块，但内部仍逐元素读取压缩值、做位运算、转 BF16、
调用 `LocalTensor.SetValue`；每行输出仅 256 字节，并在搬出前后使用 `PIPE_ALL` 屏障。
这意味着核数并行已经有了，核内向量化、较大块搬运及计算/搬运重叠仍不足。
源码见 [PspkvGatherPagedBF16](../../native/pspkv_fp8.asc)。

这里的 94.83% 是该内核内部的流水线计数比例，不能解释成整张卡的利用率，
也不能把 0.20% 向量比例解释成整张卡只有 0.20% 在工作。
原生注意力已经执行矩阵路径，因此不能继续把跨页差距归因于“整个注意力都没用矩阵单元”。

三个格式的独立调用还显示了解码的长度增长趋势。以下是主机计时的每次调用毫秒数，
含对应调用的分配、提交和等待；与上面的纯内核时间采用不同口径：

| 长度 | Basic 解码 | Enhanced 解码 | BTKV 解码 | 已解码缓存上的原生注意力，三格式范围 |
| --- | ---: | ---: | ---: | ---: |
| 160 | 0.170 | 0.217 | 0.214 | 0.051～0.055 |
| 512 | 0.514 | 0.628 | 0.628 | 0.053～0.057 |
| 2048 | 1.995 | 2.462 | 2.460 | 0.052～0.054 |

在这些隔离测试中，解码成本随长度明显增长；原生注意力控制变化较小。
不能外推后者在任意长度下都是常数。Enhanced/BTKV 的 V 布局为转置布局，
当前逐 token 重建方式需要跨步读取，地址计算和访问方式与 Basic 不同。
没有采集到数据缓存命中率或实际 HBM 带宽，不能据此声称带宽已经跑满。

从逻辑数据流看，FP8 每元素至少经历约 1 字节压缩读取、2 字节临时写入和
2 字节临时读取；BF16 基线可直接读取 2 字节缓存。
这只是额外物化成本的示意，没有计入 padding、缓存复用和其他访存，
不是实测 HBM 流量，也不是“总显存带宽消耗恰好 2.5 倍”的结论。

## 短输入：仍在使用旧标量注意力

上一轮为了避免所有输入切换原生路径后短句退化，保留了长度小于 64 的旧分支。
短输入从 3 token 开始生成 32 token，整个生成过程都未达到这一阈值。

长度 32 的 Basic 实际回调采样为：

| 内核 | 平均设备执行时间 | AIV 标量流水线比例 |
| --- | ---: | ---: |
| PackedScores：QK | 169.35 μs | 99.03% |
| Softmax | 9.05 μs | — |
| PackedWeightedValue：V 加权 | 214.61 μs | 99.77% |
| 原生分页注意力控制，仅计算 | 15.37 μs | 混合矩阵/向量算子 |

因此短输入确实仍有核内标量计算瓶颈。原生控制使用预先解码的缓存，未包括
压缩写入、解码、元数据准备，不能把 15.37 μs 当作可直接替换整个回调的成本。
也不能据此直接把阈值调低：上一轮全走新路径的整模型试验没有稳定改善短句。
需要针对小上下文减少固定开销，并设计向量化或融合的短序列实现。

## 适配层：每层重复做了额外准备

最终对照回调每层都会拼接 K/V、创建长度张量、清零输出并调用多个算子。
单独测试长度 160 的结果如下；这些是框架调用的主机计时，不能当作纯设备执行时间：

| 操作 | 每次调用范围，三格式 |
| --- | ---: |
| 构造一个新的 NPU int32 长度张量 | 0.072～0.074 ms |
| 构造一个新的 CPU int32 长度张量 | 0.017～0.018 ms |
| `stack(key, value)` | 0.027～0.029 ms |
| 单 token 并行压缩写入，输入已拼接 | 0.024～0.026 ms |
| 仅创建两块同形状临时张量 | 0.018～0.019 ms |

长度与页表元数据在同一解码步的 28 层之间通常可以共用，当前回调仍重复准备，
增加主机开销和小任务提交。这是适配方式的成本，不能全部归因于 FP8 格式本身。
两块临时张量主要由缓存分配器提供，`empty` 不代表每次都向驱动申请显存；
仅分配的耗时明显小于真正的解码耗时，故单纯复用 workspace 无法消除主要差距。

完整适配器回调的长度 160 主机计时为 Basic 0.535 ms、Enhanced 0.510 ms、
BTKV 0.504 ms。隔离测试有缓存与调度差异，因此即使 Basic 单独解码更快，
也不能断言它完整回调必然更快，更不能由这个微基准推导整模型的格式排名。

## 当前负载对 KV 压缩的速度收益不敏感

整模型测试采用单请求、135-token 输入，不是大并发或长上下文吞吐测试。
以 160 个有效 token 估算，28 层的实际活跃 BF16 K/V 总数据只有：

```text
160 × 4 KV heads × 128 dims × K/V 两份 × 2 bytes × 28 layers
= 8.75 MiB
```

压到 FP8 约省 4.375 MiB 的活跃数据，而本模型 BF16 权重约 14.28 GiB。
分配器预留很大的 KV 池，不代表每一步都读整个池。
因此当前短上下文、batch 1 的场景，压缩省下的活跃 KV 读取可能不足以抵消解码与提交开销。
模型权重、MLP、线性层和调度各占多少仍需完整模型时间线确认，这里只给出负载规模推断。

容量翻倍和请求延迟降低是两个不同指标。压缩布局使固定预算可容纳更多 token；
要把它转成吞吐收益，需要并发和上下文负载测试，且必须先控制当前随长度增长的解码成本。

## 下一轮优化顺序

1. 优先改造解码：按 tile 批量搬入 UB，向量化 FP8 解码、缩放与类型转换，
   减少逐元素 `GetValue/SetValue`、细碎屏障与小块搬运，尝试双缓冲。
   针对转置 V 调整访问方式，保留当前数值回归约束。
2. 根本方向是分块解码后在片上接注意力计算，避免每层每步把完整历史写回 BF16 临时页。
   长期保存完整 BF16 影子缓存会抵消容量收益，不适合作为主要方案。
3. 把每步长度、页表元数据移到层外复用，复用按流管理的临时空间，
   让压缩写入直接接收 K/V，减少 `stack` 和重复清零等固定成本。
4. 针对短上下文设计低固定开销的向量化或融合分支，再用整模型试验调整阈值。
   不能只凭原生算子单次执行时间决定选路。
5. 以上改动分别做算子数值回归，再重复相同 BF16 对照；随后扩大到长上下文和并发吞吐。
   三格式当前均走相近的参考计算路径，BTKV 名称不意味着已经具有 Blackwell 原生能力。

本次数据不支持给出“再增加多少核就能超过 BF16”或具体下一轮加速百分比。
原量化编码和生成质量问题也未由性能分析解决，应继续独立跟踪。
